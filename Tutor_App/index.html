Session 1: TypeScript Basics & Asynchronous Execution

คู่มือลงลึกโครงสร้างไวยากรณ์ TypeScript และกระบวนการทำงานแบบ Async/Await

1. พื้นฐานไวยากรณ์ TypeScript (TypeScript Syntax Basics)

TypeScript เป็นภาษาที่เป็น Static Typing (ระบุชนิดตัวแปรชัดเจน) ซึ่งแตกต่างจาก JavaScript ที่เป็น Dynamic Typing (ตัวแปรเปลี่ยนชนิดไปมาได้อิสระ) การระบุชนิดของข้อมูลช่วยตรวจจับบั๊กได้ตั้งแต่ตอนเขียนโค้ด (Compile-time) ป้องกันค่าประเภท undefined หรือ null หลุดไปรันจริง

1.1 การระบุชนิดตัวแปรพื้นฐาน (Basic Variable Types)

// ระบุชนิดชัดเจน (Explicit Typing)
const username: string = "namo_tester";
const age: number = 24;
const isQA: boolean = true;

// กรณีเป็น List/Array
const skillList: string[] = ["Playwright", "Robot Framework", "Appium"];
const scoreList: Array = [100, 95, 98];

1.2 โครงสร้างข้อมูลแบบ Object (Type Alias & Interface)

ในงานเทสระบบธนาคาร เรามักจะส่งหรือรับข้อมูลที่มีโครงสร้างซับซ้อน เช่น ข้อมูลบัญชี ข้อมูลผู้ใช้ เราสามารถควบคุมโครงสร้างนี้ได้ด้วย interface หรือ type:

interface UserAccount {
    accountNo: string;
    holderName: string;
    balance: number;
    status: "active" | "suspended"; // กำหนดค่าเฉพาะตัว (Union Type)
}

const client: UserAccount = {
    accountNo: "004-1-23456-7",
    holderName: "Namo Mahidol",
    balance: 50000.00,
    status: "active"
};

1.3 การระบุประเภทข้อมูลสำหรับฟังก์ชัน (Function Types)

ฟังก์ชันใน TS จะต้องระบุประเภทพารามิเตอร์ขาเข้า และประเภทข้อมูลที่จะส่งกลับ (Return Type) เสมอ:

// ฟังก์ชันปกติ (Synchronous) รับ string 2 ตัว ส่งกลับเป็น boolean
function checkCredentials(user: string, pass: string): boolean {
    return user === "boss" && pass === "pass123";
}

2. กระบวนการทำงานแบบ Asynchronous (Async/Await)

เนื่องจากตัวรัน JavaScript (Event Loop) ทำงานแบบ Single Thread (มีสมองสั่งงานเดียว) ทำให้กระบวนการที่กินเวลา เช่น การดาวน์โหลดเว็บ การเชื่อมต่อฐานข้อมูล หรือการดึงข้อมูลจาก API ต้องถูกส่งไปประมวลผลเบื้องหลังในรูปแบบของ Promise เพื่อไม่ให้แอปพลิเคชันค้าง

💡 Promise คืออะไร?
คือ วัตถุ (Object) ที่เป็นตัวแทนของผลลัพธ์การทำงานแบบ Async โดยมี 3 สถานะ:
  • Pending: อยู่ระหว่างดำเนินงาน (กำลังดาวน์โหลด หรือรอผลลัพธ์)
  • Fulfilled (Resolved): ทำงานเสร็จสมบูรณ์ ได้ข้อมูลกลับมา
  • Rejected: เกิดข้อผิดพลาด (เช่น ลิงก์ล่ม, พอร์ตปิด)

2.1 การเขียน Async/Await และการจัดการ Error

ในการเขียนโปรแกรมเทสอัตโนมัติ เราใช้ await เพื่อรอให้ Promise ทำงานสำเร็จก่อนรันคำสั่งถัดไป และเมื่อใช้ await เราจะต้องครอบด้วยบล็อก try / catch เพื่อป้องกันแอปพลิเคชันแครชเมื่อพบสถานะ Rejected เสมอ:

// ฟังก์ชัน Async ดึงยอดเงินบัญชี
async function fetchBalanceFromAPI(accountNo: string): Promise {
    // สมมติว่ายิง API ข้ามเน็ตเวิร์ก
    return 15000.00;
}

// การเรียกใช้งานแบบมีโครงสร้างรับมือ Error
async function runVerificationProcess(accountNo: string) {
    try {
        console.log("Starting account verification...");
        // รอผลลัพธ์ด้วย await
        const balance = await fetchBalanceFromAPI(accountNo); 
        console.log(`Verification success. Balance: ${balance}`);
    } catch (error) {
        console.error("Verification failed! Details: ", error);
    }
}

โจทย์ระดับ Senior: บอสต้องเขียนสคริปต์ตรวจสอบยอดเงินรวมของบัญชีผู้ใช้จำนวน 3 บัญชี: 1. ยิงดึงข้อมูลยอดเงินแต่ละบัญชีขนานกันโดยใช้ Promise.all() เพื่อไม่ให้บล็อกระบบ (ประหยัดเวลา) 2. บัญชีที่ 3 มักพบข้อขัดข้องและส่งผลลัพธ์ล้มเหลวแบบสุ่ม (Flaky API) บอสต้องเขียนฟังก์ชันย่อยสำหรับการดึงข้อมูลบัญชีแบบมีกลไก Retry (ลองใหม่ได้สูงสุด 3 ครั้ง) หากลองครบแล้วยังพังจึงโยน Error 3. ประกาศ Type ตัวแปรและฟังก์ชันให้ถูกต้องตามมาตรฐาน TypeScript ทั้งหมด (ครอบคลุมการจัดการ try/catch และชนิดข้อมูลส่งกลับ)

Session 2: Appium Mobile Testing with TS

เจาะลึกการระบุตำแหน่งอ็อบเจกต์และกระบวนการรันคำสั่งบน Mobile Automation

1. กลยุทธ์การระบุ Locators บน Native Mobile App

สถาปัตยกรรมของแอปมือถือ (iOS และ Android) มีวิธีการแสดงผลแอปต่างจากหน้าเว็บเบราว์เซอร์ การระบุตำแหน่ง Element จึงต้องอาศัยกลยุทธ์ที่เร็วและเสถียรที่สุดเรียงตามลำดับความสำคัญ:

ชื่อ Locator เครื่องหมาย/ไวยากรณ์ ความเร็วและความเสถียร คำอธิบาย
Accessibility ID ~accessibility-id ⭐⭐⭐⭐⭐ (ดีที่สุด) รันเร็วและเสถียรที่สุด ทำงานข้ามแพลตฟอร์มได้ทั้ง iOS (Accessibility Identifier) และ Android (Content Description)
Resource ID id/element_id ⭐⭐⭐⭐ ใช้สำหรับ Android เป็นหลัก โดยระบุตำแหน่งตรงไปยัง ID ของปุ่มในโค้ด UI XML
XPath //android.widget.Button[...] ⭐ (ควรหลีกเลี่ยง) ทำงานช้ามากเนื่องจาก Appium ต้องไล่แกะโครงสร้าง UI Tree ทั้งหน้า หากโครงสร้างหน้าจอขยับนิดเดียว สคริปต์จะพังทันที

2. โครงสร้างคำสั่ง Appium (WebdriverIO Framework)

ชุดคำสั่งพื้นฐานของการโต้ตอบกับแอปมือถือที่ควรรู้:

  • const el = await $('~selector'): ค้นหา Element เดี่ยว
  • await el.setValue('text'): ป้อนข้อความลงใน Input Field
  • await el.click(): คลิกองค์ประกอบบนหน้าจอ
  • await el.isDisplayed(): ตรวจเช็กว่า element แสดงผลบนหน้าจอหรือไม่ (คืนค่าเป็น true/false)
  • await el.waitForDisplayed({ timeout: 5000 }): สั่งให้หยุดรอให้ Element ปรากฏขึ้นมาภายในเวลาที่กำหนด (มักใช้จัดการหน้าจอที่รอการดาวน์โหลด)

3. ตัวอย่างการเขียนสคริปต์ทดสอบ Appium TS (Mocha Test Case)

ในการทำ Automated Test ด้วย Appium (ผ่านเฟรมเวิร์ก WebdriverIO) สคริปต์การทำเทสจะมีโครงสร้างคล้ายการเขียน Mocha/Jasmine ที่ใช้ describe ในการจัดกลุ่ม และ it ในแต่ละเทสเคสย่อย ดังตัวอย่างด้านล่างนี้ค่ะ:

import { expect } from 'chai'; // ตัวเปรียบเทียบค่าความถูกต้อง

describe('Krungsri 1KS Mobile App - Payment Suite', () => {
    
    // ทำงานก่อนเริ่มทุกเทสเคส (มักใช้ล็อกอินเข้าระบบไว้รอ)
    before(async () => {
        console.log('App launch initiated.');
    });

    it('should complete bill payment successfully', async () => {
        // 1. ค้นหาช่องระบุเลขบิลชำระเงินโดยใช้ Accessibility ID
        const billNumberInput = await $('~input-bill-number');
        
        // 2. สั่งให้โปรแกรมหยุดรอจนกว่าช่องป้อนข้อมูลจะแสดงขึ้นมาบนหน้าจอจริง (ไม่เกิน 10 วินาที)
        await billNumberInput.waitForDisplayed({ timeout: 10000 });
        
        // 3. ป้อนหมายเลขบิลจำลอง
        await billNumberInput.setValue('1234567890');
        
        // 4. ค้นหาช่องป้อนยอดเงินและระบุจำนวนเงิน
        const amountInput = await $('~input-pay-amount');
        await amountInput.setValue('500');
        
        // 5. ซ่อนคีย์บอร์ดโมบายล์หลังจากพิมพ์เสร็จ เพื่อป้องกันการบล็อกปุ่มยืนยัน
        if (await driver.isKeyboardShown()) {
            await driver.hideKeyboard();
        }

        // 6. คลิกปุ่มยืนยันการชำระเงิน
        const confirmButton = await $('~btn-confirm-payment');
        await confirmButton.click();

        // 7. รอให้กล่องข้อความตอบรับสำเร็จแสดงผล
        const successMessage = await $('~txt-success-alert');
        await successMessage.waitForDisplayed({ timeout: 15000 });
        
        // 8. ดึงข้อความและ Assert ตรวจยืนยันความถูกต้อง
        const actualText = await successMessage.getText();
        expect(actualText).to.equal('ชำระเงินสำเร็จ');
    });
});
⚠️ การทดสอบบนแอปธนาคารที่ต้องระวัง:
ระบบธุรกรรมธนาคารมักมีหน้าจอแจ้งเตือนขอสิทธิ์ (System Permissions dialog) เช่น การเข้าถึงกล้อง/คลังภาพ บอสควรใช้สคริปต์จัดการปุ่มแจ้งเตือนของระบบโดยอัตโนมัติด้วยคำสั่ง: await driver.acceptAlert(); หรือระบุปุ่มตกลงในระบบของ OS

โจทย์ระดับ Senior: บอสต้องเขียนสคริปต์ทดสอบอัตโนมัติบน Appium สำหรับขั้นตอนการชำระเงินที่ซับซ้อนขึ้น ดังนี้: 1. หน้าจอมีรายการ Biller หลายสิบเจ้า บอสต้องเขียนลูป Swipe Down ค้นหาจนเจอปุ่ม Biller ชื่อ "Krungsri Card" ที่มี ID ~biller-krungsri-card แล้วคลิก (แนะนำให้ใช้ลูปตรวจสอบด้วย isDisplayed() และใช้ driver.touchAction() หรือคำสั่ง swipe ของ WebdriverIO ในการสไลด์หน้าจอ) 2. หลังจากคลิกแล้ว ระบบจะแสดงตัวโหลดหมุนกลมๆ ~loading-spinner บอสต้องเขียนคำสั่งหยุดรอจนกว่า ตัวหมุนจะหายไปจากหน้าจอ (Invisibility Wait) 3. หน้าถัดไปเป็น Security PIN Keypad! บอสต้องเขียนคำสั่งคลิกรหัส PIN "1234" ทีละตัวผ่านปุ่มตัวเลข เช่น ~pin-key-1, ~pin-key-2... ตามลำดับ 4. ตรวจเช็กว่าหน้าชำระเงินสำเร็จขึ้นข้อความ ~txt-payment-success มีข้อความแสดงสถานะชำระเงินเรียบร้อยแล้วจริงหรือไม่ (กรุณา Assert ผลลัพธ์ที่ถูกต้อง)

Session 3: Playwright Web Testing & Page Object Model (POM)

แนวคิดการทำ Page Object Model ใน TypeScript เพื่อความง่ายในการรักษาโค้ดเทส

1. แนวคิด Page Object Model (POM) คืออะไร?

POM เป็นรูปแบบการออกแบบสคริปต์เทส (Design Pattern) ยอดนิยมในวงการ Automation โดยหลักการคือการแบ่งแยกหน้าที่ในโค้ดออกเป็น 2 ชั้นหลัก:

  1. Page Object Class: เก็บตำแหน่ง Selector และพฤติกรรม (Action Methods) ทั้งหมดของหน้าเว็บหน้านั้นๆ
  2. Test Script: ไฟล์สคริปต์เทสจริงที่เขียนเรียงลำดับ User Journey โดยใช้วิธีเรียกใช้งาน Method จาก Page Object Class แทนการหา Selector ในไฟล์เทสโดยตรง
ประโยชน์ของ POM: เมื่อผู้พัฒนา (Dev) ปรับเปลี่ยนหน้าเว็บหรือ ID ของปุ่ม เราเพียงแก้ไข Selector ที่ไฟล์ Page Object Class ที่เดียว โดยไม่ต้องไล่ตามแก้ไขสคริปต์เทสที่มีเป็นร้อยๆ ไฟล์ค่ะ

2. เปรียบเทียบโครงสร้าง: Python Playwright vs TypeScript Playwright

ในภาษา TypeScript (TS) จะแตกต่างจาก Python ตรงที่มีความเข้มงวดเรื่องชนิดข้อมูล (Type Safety) ซึ่งช่วยให้ระบบ IDE แนะนำฟังก์ชันการพิมพ์ (Autocomplete) ได้แม่นยำยิ่งขึ้น:

หัวข้อ Python Playwright TypeScript Playwright
การประกาศ Properties ไม่ต้องระบุประเภทข้อมูลล่วงหน้า ต้องระบุ เช่น readonly page: Page; และ readonly usernameInput: Locator;
Constructor def __init__(self, page): constructor(page: Page) { ... }
การชี้ตำแหน่ง Locator self.username = page.locator("#user") this.usernameInput = page.locator('#user');
การเรียก Action self.username.fill("value") await this.usernameInput.fill('value'); (ต้องมี await)

3. ตัวอย่างโครงสร้าง Page Object Class & Test Spec ใน TypeScript

ตัวอย่างคลาส LoginPage.ts:

import { Page, Locator } from '@playwright/test';

export class LoginPage {
    // 1. ประกาศ Property และชนิดข้อมูลล่วงหน้า
    readonly page: Page;
    readonly usernameInput: Locator;
    readonly passwordInput: Locator;
    readonly loginButton: Locator;

    // 2. กำหนด Locator ใน Constructor
    constructor(page: Page) {
        this.page = page;
        this.usernameInput = page.locator('#username');
        this.passwordInput = page.locator('#password');
        this.loginButton = page.locator('#btn-submit');
    }

    // 3. สร้าง Action Method
    async login(user: string, pass: string) {
        await this.usernameInput.fill(user);
        await this.passwordInput.fill(pass);
        await this.loginButton.click();
    }
}

ตัวอย่างการเรียกใช้งานในสคริปต์เทส login.spec.ts:

import { test, expect } from '@playwright/test';
import { LoginPage } from './LoginPage';

test('ทดสอบการเข้าสู่ระบบสำเร็จ', async ({ page }) => {
    const loginPage = new LoginPage(page);
    
    await page.goto('https://example.com/login');
    await loginPage.login('namo_qa', 'secured_pass');
    
    // ยืนยันผลลัพธ์
    await expect(page.locator('#welcome-message')).toHaveText('ยินดีต้อนรับบอส!');
});
💡 ทริคระดับ Mid-Level - การล้างและดึงยอดเงินพลวัต (Extracting Dynamic Balance):
ในระบบงานธนาคาร ยอดเงินมักแสดงเป็นข้อความเช่น "ยอดคงเหลือ: 5,000.00 บาท" เพื่อจะนำมาคำนวณเปรียบเทียบ บอสสามารถดึงข้อความเป็น string แล้วตัดส่วนอักษรอื่นด้วย Regular Expression (Regex) และแปลงเป็น float ดังนี้ค่ะ: 
const rawText = await page.locator('#txt-balance').innerText(); // "ยอดคงเหลือ: 5,000.00 บาท"

การเชื่อมโยงข้อมูลข้าม API และการตรวจสอบผลลัพธ์ที่ระดับฐานข้อมูล (SQL)

1. ออกแบบ API และทดสอบ JSON Schema Validation

ในการทำธุรกรรมชำระเงิน (Bill Payment) ข้อมูลจะต้องถูกส่งข้ามแอปพลิเคชันอย่างปลอดภัย โดยใช้ HTTP Method: POST และส่งพารามิเตอร์สำคัญผ่าน Request Body (JSON Format)

โครงสร้าง JSON Schema: เป็นเครื่องมือที่ใช้ตรวจสอบความถูกต้องของประเภทข้อมูลที่ตอบกลับมาจาก API (Response Body) เพื่อยืนยันว่าโครงสร้าง ชนิดข้อมูล และเงื่อนไขตรงตามเอกสารข้อกำหนดเชิงเทคนิคค่ะ

💡 ตัวอย่างโครงสร้าง JSON Request Payload:

{
    "payer_account_no": "111-2-33333-4",
    "payee_biller_code": "9999",
    "amount": 2500.50,
    "currency": "THB"
}

💡 ตัวอย่างการเขียน JSON Schema Validation:

{
    "$schema": "http://json-schema.org/draft-07/schema#",
    "type": "object",
    "properties": {
        "transaction_id": {
            "type": "string",
            "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$" // Regex เช็ค UUID ฟอร์แมต

        "status": {
            "type": "string",

        },

        },

}

โจทย์ระดับ Senior: บอสต้องออกแบบ API และการทวนสอบการตอบกลับ (Response Verification) สำหรับระบบโอนเงินข้ามประเทศ (Cross-Border Transfer): 1. ร่างตัวอย่าง JSON Body ของ POST /api/v2/transfers โดยต้องมีฟิลด์ข้อมูลลูกค้า (Payer Name, Account Number) และข้อมูลผู้รับ (Payee Name, Account, SWIFT Code) พร้อมยอดเงินและสกุลเงินที่ต้องการโอน (เช่น USD, THB) 2. เขียนโครงสร้าง JSON Schema เพื่อตรวจสอบผลลัพธ์การตอบกลับที่ได้รับหลังจากส่งคำสั่งสำเร็จ โดยต้องระบุเงื่อนไข: - ฟิลด์ transaction_id ต้องเป็นประเภท string และตรงตามแพทเทิร์น UUID เท่านั้น (เช่น มี regex pattern) - ฟิลด์ transfer_status ต้องมีค่าเป็นหนึ่งใน enum: "PENDING", "SUCCESS", "FAILED" เท่านั้น - ฟิลด์ fee_amount ต้องเป็นประเภทตัวเลข (number) ที่มีค่าไม่ต่ำกว่า 0 - ต้องบังคับ (required) ว่าต้องมีฟิลด์ transaction_id, transfer_status, และ processed_at เสมอค่ะ

2. การตรวจสอบข้อมูลผ่านคำสั่ง SQL (Database Verification)

QA Automation ที่ดีต้องไม่ละเลยข้อมูลหลังบ้าน (Database) เพื่อให้มั่นใจว่าเมื่อหน้าจอบอกว่าชำระเงินสำเร็จแล้ว ยอดเงินได้ถูกหักออกจากบัญชีของผู้จ่าย และรายการธุรกรรมถูกบันทึกลงฐานข้อมูลถูกต้องจริง

💡 ตัวอย่างคำสั่ง SQL Query แบบ JOIN พื้นฐาน:

-- ดึงข้อมูลยอดโอนเงินของลูกค้าโดย JOIN ตารางผู้ใช้และบัญชีเข้าด้วยกัน
SELECT u.first_name, a.account_no, p.amount, p.created_at
FROM users u
INNER JOIN accounts a ON u.user_id = a.user_id
INNER JOIN payments p ON a.account_id = p.account_id
WHERE a.account_no = '004-1-23456-7'
ORDER BY p.created_at DESC;

💡 ตัวอย่างคำสั่ง SQL ค้นหารายการซ้ำซ้อนภายในช่วงเวลา (Self-JOIN / Double Payment Check):

-- ค้นหาธุรกรรมโอนเงินที่กดซ้ำ (ยอดเงินเท่ากัน บัญชีเดียวกัน โอนห่างกันไม่เกิน 5 นาที)
SELECT 
    p1.payment_id AS first_payment_id,
    p2.payment_id AS duplicate_payment_id,
    p1.account_id,
    p1.amount,
    p1.created_at AS first_time,
    p2.created_at AS duplicate_time
FROM payments p1
INNER JOIN payments p2 ON p1.account_id = p2.account_id
    AND p1.amount = p2.amount
    AND p1.payment_id < p2.payment_id -- ป้องกันการสลับคู่เดิมซ้ำ และไม่จับคู่ตัวเอง
WHERE 
    -- ใน PostgreSQL เช็คช่วงเวลา 5 นาที:
    p2.created_at <= p1.created_at + INTERVAL '5 minutes'
    -- (หากใช้ MySQL: TIMESTAMPDIFF(SECOND, p1.created_at, p2.created_at) <= 300)

โจทย์ระดับ Senior: บอสต้องเขียนคำสั่ง SQL Query เพื่อสืบสวนหาบั๊กหลังบ้านของธนาคารที่มีการจ่ายเงินซ้ำซ้อน: 1. ค้นหาข้อมูลธุรกรรมชำระเงินที่เกิดขึ้นซ้ำ โดยตรวจสอบจากลูกค้าคนเดิม (account_id เดียวกัน) ยอดเงินเท่ากัน (amount เท่ากัน) และจ่ายให้ผู้รับเดียวกัน (biller_code เดียวกัน) ที่เกิดขึ้นห่างกัน ไม่เกิน 60 วินาที (1 Minute Interval) 2. ให้เชื่อมโยงข้อมูล (JOIN) 3 ตารางคือ users, accounts, และ payments 3. ผลลัพธ์ต้องแสดง: ชื่อผู้ใช้ (first_name), เลขบัญชีต้นทาง (account_no), จำนวนเงิน (amount), รหัสธุรกรรมครั้งแรก (payment_id ตัวแรก), และรหัสธุรกรรมตัวที่สองที่ซ้ำ (payment_id ตัวที่สอง) เพื่อส่งข้อมูลนี้ไปวิเคราะห์หาบั๊กต่อไปค่ะ

การทดสอบเคสเฉพาะของ Mobile Banking บนแอป LINE เช่น เน็ตหลุดระหว่างกดยืนยันโอนเงิน (Network Interruption), มีสายโทรเข้าขณะป้อน PIN (App Interruption), และการพับแอปแล้วกลับเข้ามาต้องล็อก PIN ป้องกันความปลอดภัย
🔹 3. Root Cause Verification (Postman API & SQL DB):
แม้งานหลักจะเป็น Manual Test แต่เมื่อพบข้อผิดพลาด บอสสามารถยิง Postman ตรวจสอบ API และรัน SQL Query ส่องฐานข้อมูลเพื่อวิเคราะห์สาเหตุเบื้องต้นและแจ้งทีม Dev ได้อย่างแม่นยำ
🔹 4. AI-Augmented Manual QA Advantage:
นำ AI มาช่วยคิดหา Edge Cases และเงื่อนไขย่อยแปลกๆ เพิ่มเติมได้อย่างรวดเร็ว ทำให้การทำ Manual Test มีความครอบคลุม (Test Coverage) สูงสุด
